# Resilience Testing

Open a project and select **Resilience Testing** in the workspace. The scenario editor loads the registered coupled-tank model with its nominal operating point. Set tank levels and hydraulic parameters, select acquisition channels, and add faults to the schedule. Each fault has a stable ID. Preview the schedule to resolve its time intervals, then run the scenario and compare measured channels with physical trajectories. Saved scenarios can be edited and rerun. Earlier runs retain their input snapshot and numerical evidence.

In **Campaigns**, choose a detector configuration and a base scenario. A grid can vary any combination of severity, onset and recovery, sensor noise, missing fraction, initial levels, model parameters and seeds. The `faults` axis takes complete event arrays, so it can include a healthy control and alternative fault combinations in the same campaign. An axis such as `faults.pump.severity` targets the event with ID `pump`. Axes under `detector.training` vary the nominal reference for model mismatch studies. Search uses one fixed detector and uniform, seeded draws within numeric bounds. The benchmark loads a fixed set of evaluation scenarios and detector configurations.

Open a completed case to inspect measured and physical curves, detector scores, alarms, event matches, and data quality. **Export Dataset** saves the values available on the acquisition clock. The Signal Explorer can open those channels, and the existing Incident dialog can attach the Dataset as evidence. The offline campaign report includes the saved plan and case results. All scenarios, runs and campaigns are stored locally. A service restart preserves completed results and marks unfinished cases interrupted.

## Numerical and observation model

The lab uses the coupled-tank model's donor-limited SSPRK2 integrator. Simultaneous pump or valve losses compose multiplicatively. Multiple leaks on the same tank add discharge coefficients. The tanks exchange one shared signed transfer flow, so it cancels from the total-volume balance. Inlet, outlet, leak and overflow integrals use the same limited stage fluxes as the volume update. The run records the volume balance residual and effective flow rates. The solver splits integration steps at off-grid physical fault transitions and uses the left limit for the closing stage.

Fault activation begins at onset and lasts until the exclusive recovery time. With no recovery time, a persistent fault remains active at the horizon. Severity is between zero and one. A step has constant severity. A linear profile reaches full severity after `rise_time`. Progressive degradation approaches full severity as `1 - exp(-elapsed / time_constant)`. A temporary step requires a recovery time. Repeating intervals use `period` and `active_duration`. Intermittent intervals independently include each candidate pulse with `cycle_probability`. Recovery removes the fault mechanism while the process state continues from its current value.

The measurement layer operates on physical samples. Its configuration includes bias, drift, stuck values, frozen source timestamps, spikes, increased noise, dropouts, blackouts, delays and out-of-order packets. The saved packet log distinguishes sample time, source timestamp and arrival time. Acquisition polls consume arrivals up to that poll and retain the most recent arrival per signal. When several packets arrive between polls, the packet log still retains all of them. Unavailable values remain null, with quality recorded in the lab. Separate seed-derived streams control physical inlet disturbance, baseline sensor noise, baseline packet loss and event-specific random effects. Stream keys use signal and stable event IDs.

## Detector evaluation

Each detector fits and calibrates on a separate healthy reference simulation, using the configured nominal model and operating conditions. The test inputs are the selected acquired values and acquisition clock. The detector sees neither fault schedules, quality labels generated from injected causes, nor physical truth. Missing values enter the existing L5 observation policy, and the case records its effective coverage and abstentions.

- **Presence** means at least one alarm sample overlaps an active fault interval. An alarm already active at onset can count as presence.
- **Event detection** matches distinct alarm episode starts to events that are active at those times. Maximum-cardinality matching assigns each episode start and event at most once. Delay is measured from event onset. Event rate includes unobserved events as misses and reports their count separately. The match describes timing. Fault-type identification would require a detector that produces fault-type predictions.
- **Normal alarm burden** uses the full timeline for healthy controls. For faulted runs it uses the pre-fault window. Inactive time after recovery is tracked separately because process levels may still be settling.
- **Failure search** ranks cases by miss rate, normalized delay, healthy alarm fraction, missing coverage or suppression. Suppression compares presence in a multi-event case with presence for each event simulated in isolation at the same seed and conditions. Distinct-event matches are also recorded for those comparisons.

The service bounds per-scenario samples, integration steps and event counts. Campaigns allow up to 64 detector cases, searches allow up to 32 candidates, and a total integration budget limits expensive combinations. Runtime and execution errors remain visible per case.

## Fixed benchmark

Run **Benchmark** in the lab, or run `node scripts/python.mjs -m benchmarks.resilience` from the repository. Use `--output-dir <directory>` to save the Markdown and JSON reports. The protocol uses separate seeds for development (`42017`), search draws (`62043`), final evaluation (`92351`, with `92352` for a second healthy control), and nominal training (`14071`). It evaluates Robust Max-Z, EWMA and PCA-Q on both tank levels, plus a Tank 1-only Robust Max-Z configuration.

All 64 detector runs completed. The largest absolute mass-balance residual was below `1.3e-13 m³`. Both nominal healthy controls produced zero alarms across all four configurations. Under the shifted initial condition and outlet coefficient, all four alarmed on 599 of 601 polls in the healthy control. Adding a pump fault to that shifted operating point left the preexisting alarm active, giving presence without a new matched alarm. For the leak that began at 48 s during the blackout, all four first alarmed at 64.4 s, with 81.7% decision coverage. The blackout event itself was wholly unobserved and unmatched.

Tank 1-only Robust Max-Z detected the short pump loss and valve restriction in isolation and missed their simultaneous combination at full coverage. Peak physical Tank 1 deviations during the active interval were 33.32 mm, 33.04 mm and 0.81 mm for the pump, valve and combined cases, respectively. The corresponding peak Max-Z scores were 16.41, 17.44 and 2.04 against a threshold of 3.38. At the nominal operating point, the two faults reduce the Tank 1 inlet and transfer flows by the same amount at onset. This cancels the initial change in the Tank 1 volume derivative, while Tank 2 loses transfer inflow and moves 33.08 mm. Dual-level Robust Max-Z and EWMA detected both isolated faults. Dual-level PCA-Q missed the isolated short valve restriction. All three dual-level configurations detected the combination and matched one of its two events. The result depends on the operating point, equal initial flow losses, fault duration, sensor selection and detector configuration.
